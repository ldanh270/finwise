# Web transaction correction walkthrough

Date: 2026-08-31
Phase: 7 — Web MVP hardening and pilot release
Status: Implemented as a command-boundary slice; production auth, persistence, and pilot gates remain.

## Scope and non-goals

The web transactions screen now exposes a reasoned Void action for posted rows. The action calls the immutable-ledger reversal endpoint, carries a stable idempotency key, refreshes the workspace after success, and labels already-voided rows without offering another mutation.

This slice does not add replacement editing, classification split editing, audit explorer screens, role administration, Supabase OTP/protected layouts, or browser E2E tests.

## Affected files and modules

- `backend/src/core/application/core.service.ts` — includes journal status in overview transaction summaries.
- `frontend/src/lib/api/contracts.ts` — adds posted/voided transaction status.
- `frontend/src/lib/api/client.ts` and `frontend/src/features/ledger/ledger-service.ts` — typed void command transport and feature wrapper.
- `frontend/src/features/dashboard/dashboard-page.tsx` — row-level confirmation form and status affordance.
- `frontend/app/globals.css` — correction controls and voided-row presentation.
- `contracts/openapi.json` — documents the void endpoint and request/response shape.

## Business rules

- A posted transaction is never edited or deleted. Void posts a balancing reversal and marks the original voided.
- A reason is mandatory and the effective date defaults to today at the UI edge; backend validation remains authoritative.
- Financial command retries use an idempotency key generated by the feature service.
- Void controls are shown only on the transaction resource screen; already-voided rows expose a read-only label.
- Overview status comes from the server and is not inferred from cached UI state.

## Data flow

```text
transaction row -> reason form -> ledger service -> POST .../void
                -> CoreService voidTransaction -> reversal + audit
                -> typed response -> dashboard refresh -> voided status
```

The browser does not calculate the reversal or balance. The server remains the only ledger authority.

## Public API and UI behavior

`POST /v1/workspaces/:workspaceId/transactions/:transactionId/void` accepts `{ reason, effectiveDate? }`, requires `Idempotency-Key`, and returns `{ original, reversal }`. The overview transaction summary now includes `status: posted | voided`.

On the Transactions screen, each posted row has a Void button. The button opens a labelled reason input with Cancel and Confirm void actions, pending state, and typed error feedback. Success refreshes balances and recent activity. Voided rows are visually muted and cannot be submitted again.

## Migration and security implications

No database migration is added. The in-memory store already implements reversal and audit semantics. A production adapter must persist original status, reversal linkage, audit details, and idempotency atomically. Authorization and transaction-void permission remain enforced in Nest; the UI does not hide server errors or rely on route parameters for access.
